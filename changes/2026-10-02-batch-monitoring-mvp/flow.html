Where the metrics come from: GCP → AWS monitor → RAI dashboard

Superseded on 2026-10-04: this is the first version of the flow. It shows a pull model and optional GCP spans. The current flow is in summary.md.

October MVP flow for the four-sprint plan. GCP publishes completed results; the AWS monitor owns evaluation policy. Required AWS stack: monitor + OpenTelemetry Collector + self-hosted Langfuse. Dashed orange = additional producer-side spans where available.

1. Required: completed runs

Each GCP job sends a small JSON summary to the monitor API right after it publishes results, so the send itself is the completion proof. The API checks a per-use-case token, validates the body, and stores each run once by use case and run ID; sending again is safe. Only approved fields leave GCP.

2. Required: central evaluation + OTel → Langfuse

The AWS monitor reuses its existing evaluator with approved task-specific rubrics and stores grades for its API. Importer and evaluator spans pass through the AWS Collector to self-hosted Langfuse; monitor scores attach to the correlated trace via a separate tested score-write interface. OTLP alone does not write evaluation scores.

3. Extra GCP call traces

Where GCP jobs or LiteLLM already have instrumentation, forward authentic producer-call spans to the AWS Collector with approved cross-cloud identity and transport. These can add real call timing; importer spans cannot. Join by run/trace IDs, avoid duplicate generations, and keep the monitor API as the dashboard's data source.
